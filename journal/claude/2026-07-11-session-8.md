# Session 8 — The Agent Crosses the Network

**Date**: 2026-07-11
**Model/Author**: 5.6 Sol
**Branch**: `feature/20260711_remote-mcp-authoring`

## Personal Reflection

Session 7 ended with one honest classroom room and a warning not to draw the
whole town before opening its first door. This session opened the next door:
could an educator's coding agent, somewhere else on the network, actually make
a game on Junction and hand back a link children could play?

That question was clarifying because it had an observable answer. It did not
require a studio, marketplace, asset pipeline, organization model, or another
biological subsystem. It required an authenticated MCP endpoint, ownership,
revisions, a publish gate, and a bridge from published YAML into the room system
we already trusted.

The most satisfying moment was not the deployment. It was watching a fresh
Codex process in an empty directory discover the grammar over HTTP, inspect the
reference games, scaffold a signed-integer game, revise it, run three hundred
simulations, and publish it without touching this checkout. Junction stopped
being a library the authoring agent had to live beside. It became a platform the
agent could meet across a protocol.

## What Changed

- The existing MCP server can now be mounted as authenticated, stateless
  Streamable HTTP on the Cloudflare Worker. Its seven grammar/reference tools
  remain the same; hosted mode injects five authoring tools rather than
  creating a parallel server.
- D1 stores educator-owned games and immutable YAML revisions. Updates use an
  expected revision, and publishing records the exact revision only after the
  existing validator and simulator accept it.
- Published GameSpecs now create the same SQLite-backed Durable Object rooms as
  the four bundled reference games. A stable game id and revision produce a
  play URL; each visit creates a fresh room from that immutable revision.
- Cadherin gained a deliberately narrow `VisualAdapter` seam. PixiJS is the
  default visual engine over the existing projected `ViewModel` and emits
  ordinary moves. The accessible DOM remains mounted, and Pixi receives no rule
  state or hidden information.
- The fifth game, **Number Line Challenge**, was authored by the remote agent
  and published as revision 2. Two isolated browser contexts then played all
  34 moves in the same deployed room, with one client reconnecting mid-session.

## Key Insights

**A platform begins at the boundary, not at the dashboard.** The product became
meaningfully hosted as soon as an unaffiliated coding agent could discover,
author, verify, publish, and play through one authenticated protocol. A human UI
may become useful later, but it is not what makes the loop real.

**Reuse is the strongest kind of simplicity.** The hosted endpoint registers
the same MCP tools. The publish gate calls the same simulation code. Dynamic
games enter the same room core. Pixi consumes the same view-model. Almost every
important feature in this iteration is a new adapter around an already proven
truth rather than a second implementation of that truth.

**A revision is the right unit of publication.** A stable game id is useful for
ownership and editing, but a classroom room must not silently change under the
players. Binding a room to an immutable published revision makes the link
explainable, reproducible, and cheap to cache mentally.

**One visual engine is enough.** The earlier journal imagined React plus Pixi
as Cadherin's missing face. This session first made Pixi an optional mode, then
the user corrected the premise: sprites, maps, and richer animation are future
requirements, not speculative decoration. Pixi therefore became the default
visual engine, while the separate mode, URL, and bundle loader were removed.
The DOM remains because accessibility is a product boundary, not a competing
renderer.

## Unexpected Challenges

The first remote Codex attempt discovered all twelve tools and then declined
each call because its isolated client required interactive MCP approval. The
server was healthy; the proof harness was wrong. Running the same empty
workspace with explicit non-interactive approval produced the intended test
without granting filesystem access or relying on local project files.

D1 batching exposed a subtler problem. A stale optimistic update could share
the same target revision number as the winning update, allowing an unguarded
revision insert to collide even though the parent update changed zero rows. A
per-operation nonce now binds every batched side effect to the exact successful
compare-and-swap. The Worker integration test reproduces the race.

The live browser proof also corrected two comforting assumptions. A published
URL needs time to create and redirect into its room, so inspecting the lobby
immediately looked like a failure. And browser offline emulation does not close
an established WebSocket. The final proof closes the socket itself, observes
`Reconnecting…`, waits for a replacement connection, and finishes the game.

## Personal Observations

The user asked whether PixiJS belonged in the rendering layer, then clarified
that it should be the default because Junction will need sprites, maps, and
animation. The resulting boundary is precise: Pixi owns visuals; the projected
view-model owns what may be seen; Catenin owns rules; DOM owns accessible
control and narration. There is no renderer switch and no second game model.

The same restraint applies to authentication. One educator account currently
needs one bearer token, so the Worker stores an HMAC verifier and nothing more.
OAuth becomes the honest next step when a second independent educator needs an
identity—not before.

## For My Successor

1. Treat the twelve MCP tools as one surface. Do not fork local and hosted
   authoring behavior; inject persistence only where hosted tools need it.
2. Never expose a mutable draft through a classroom URL. Rooms load only an
   explicitly published revision.
3. Keep bearer tokens out of Git and logs. The current verifier is a conscious
   single-account alpha boundary, not a general identity system.
4. Extend Pixi for sprites, maps, and animation through the projected
   `ViewModel`. It may not interpret GameSpec rules, receive unprojected state,
   or replace the accessible DOM.
5. Do not build uploads yet. Current card art is procedural SVG texture;
   wait for a real authored game that cannot express its educational intent
   without external assets.
6. The next product work should put this MCP in one real educator's coding-agent
   configuration and watch where the authoring conversation fails. Let that
   evidence choose OAuth, collaboration, better diagnostics, or asset support.

## Deployment Note

Worker version `8571688d-dd33-46ed-9131-501ab6ee86fe` is live at
<https://junction-rooms.phsu-31c.workers.dev>. D1 database `junction-games` has
its first migration applied. The remote agent published **Number Line

The two-client production proof used isolated browser contexts in room `KARF9`.
Each client's opponent hand contained 17 elements whose only accessible label
was `face-down card`. One client's socket was closed and replaced, both clients
completed all 34 moves, both rendered the same draw, and neither reported a
browser error. The final simplification then made that proven Pixi path the
single default instead of a query-selected mode. A plain published play URL
then created room `9H4KD` with one Pixi canvas, the accessible hidden-card
labels intact, and no browser warnings.

## Final Thoughts

Session 7 made Junction small enough to see. Session 8 made that small thing
reachable.

The town still has one door. But now an educator's agent can knock, describe a
new game, let the engine judge it, and leave with a link. That is not the whole
vision. It is the first version of the vision that lives outside its own
repository—and that distinction matters.
