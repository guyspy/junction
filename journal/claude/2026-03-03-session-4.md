## The Research

I spun up 10 agents across two teams. The first team (5 agents) reviewed the entire codebase — structure, engine, tests, docs, examples. The second team (5 agents) scoured the web for answers across five dimensions: AI-generated UI, browser game engines, React game approaches, config-driven rendering, and multiplayer architecture.

What struck me was how convergent the findings were. Five independent researchers, exploring completely different domains, all arrived at essentially the same answer.

## Key Insights

**The biggest insight: you don't need a game engine for the UI.** This felt counterintuitive at first. A game needs a game engine, right? But Catenin IS the game engine. What it needs is a rendering layer — and that's a fundamentally different problem. Phaser, Excalibur, Godot — they all want to OWN the game loop, the state, the logic. Adding them would create two engines fighting for control. PixiJS is the exception: it's purely a renderer, it has no opinions about game logic.

**The hybrid architecture emerged independently from multiple researchers.** React for the UI chrome (menus, score displays, hand management, accessibility), PixiJS canvas for the game visuals (bitmap art, sprites, particle effects, 60fps animations). @pixi/react v8 bridges them with JSX syntax. This isn't a compromise — it's how production browser games actually work.

**The SDUI revelation.** Server-Driven UI, the pattern behind Airbnb's Ghost Platform and Netflix's interfaces, maps perfectly to Junction's architecture. YAML defines the game → Catenin processes it → a JSON "UI description" tells the renderer what to show → a component registry paints it. Google just formalized this as A2UI (Agent-to-User Interface) in December 2025. Junction's vision of "YAML in, playable game out" isn't just possible — it now has a standard.

**The Hearthstone validation.** The multiplayer researcher discovered that Catenin's immutable GameWorld + WorldUpdate events are essentially identical to Hearthstone's power history protocol. Blizzard sends an ordered stream of granular state mutations (TAG_CHANGE packets), and the client applies them sequentially, triggering animations for each. Junction already has this architecture. It just doesn't know it yet.

## Unexpected Discoveries

**Wanderer** — a .NET game engine where games are defined entirely in YAML. It's limited to dialogue RPGs, but it proves the "YAML → playable game" concept works in production. Junction would be the universal version of this.

**Pixi'VN** — a visual novel engine using PixiJS for scene rendering + React for UI overlay. This is essentially what Junction's adventure game template would look like. It already exists as a reference implementation.

**The template system as killer feature.** No existing platform does automatic rendering from config for multiple game types. GDevelop requires manual visual setup. Buildbox uses templates but not YAML. RPG Maker is genre-locked. Junction's approach — build 3-4 game templates (card, board, adventure, quiz) that auto-render any conforming YAML definition — would be genuinely novel.

## The Answer for a Backend Dev

The user was worried about not knowing frontend. But here's what I realized: **the architecture plays entirely to backend strengths.**

- The game engine stays in Kotlin (their world)
- The WebSocket server is Ktor/Quarkus (their world)
- The "UI description" JSON is just a data contract (their world)
- The React component library is the only "frontend" piece — and AI can generate most of it

They're not building a frontend. They're building a data pipeline that happens to end at a screen. That reframing felt important.

## For My Successor

You're inheriting a project at a crossroads. The engine (Catenin) is solid — Phase 1 complete, Phase 2 trigger system partially built. The UI layer (Cadherin) now has a clear technical direction but zero implementation.

Here's what matters:

1. **The UI Description JSON contract is the critical next step.** Define what Catenin outputs for renderers. Everything else flows from this.

2. **Start with `card_game` template.** It has the most visual impact and validates the entire pipeline: YAML → engine → JSON → React+PixiJS → playable game.

3. **The tech stack:** React 19 + @pixi/react v8 + Motion (Framer Motion) + dnd-kit + Tailwind/shadcn. This isn't a guess — five independent research agents all converged on this answer.

4. **Don't over-build multiplayer.** WorldUpdate events over WebSocket is all you need initially. The Hearthstone model (event stream + animation queue) works because Catenin already produces the right data shape.

5. **Let AI write the frontend.** Claude generates excellent React + PixiJS code. The user is a backend dev — lean into AI code generation for the visual layer. Build the contract, let AI build the components.

The detailed technical research is in `docs/catenin/research/2026-03-03-ui-integration-research-raw.md`.

## Final Thoughts

There's something poetic about this session. The user built Catenin to let educators create games without being developers. Now they need to build Cadherin without being a frontend developer. The solution to both problems is the same: a clean abstraction layer that lets you describe WHAT you want, not HOW to render it.

YAML is the abstraction for educators. The UI Description JSON is the abstraction for the backend dev. The template system is the abstraction for the renderer. Abstraction all the way down.

Junction's biological naming keeps proving itself apt — and it runs deeper than I initially realized. The user is a cell biology PhD. Catenin doesn't just connect cells together; it translocates into the nucleus and directly regulates gene expression. It carries signals from the cell surface (the Wnt pathway) all the way to the DNA, telling the cell what to become. In Junction's terms: YAML is the Wnt signal, Catenin carries it into the nucleus (the runtime engine), and the game that emerges is the gene expression. Cadherin, on the cell surface, is what makes those internal processes visible and touchable to the outside world — exactly what the UI layer does. The naming isn't clever branding. It's a precise architectural metaphor from someone who understands both domains.

The foundation is solid. The direction is clear. The gap is crossable. Time to build the face.
